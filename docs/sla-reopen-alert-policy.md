# SLA alert cycle — applied to the current database

The user selected **repeat on reopen**. The updated `00017` proposal delivers at most one alert per ticket, alert cycle, recipient and stage. Reopening a `resolved` or `closed` ticket to any non-resolved/non-closed status increments the cycle. Transitioning between resolved and closed does not. Reassigning away and back within a cycle and deleting a notification do not reset that cycle; a newly assigned recipient can receive their own alert. A requester who is also assignee receives one alert. Reopening starts a **notification** cycle, not a new SLA clock: the existing elapsed-time and hold calculations remain in place. If the ticket is already breached when reopened, the next breached job can alert; a missed earlier at-risk stage is not manufactured.

The migration adds a server-maintained `tickets.sla_alert_cycle`, a trigger that rejects client-chosen cycle values by overwriting them, and a protected ledger. Existing matching notifications are seeded **only when first creating the ledger**, all into the initial cycle; previously deleted notifications and historical reopen cycles cannot be reconstructed, so initial seed can miss earlier deliveries or suppress alerts for a prior-cycle delivery. RLS and explicit privilege revocation protect the ledger from ordinary and service roles; database owners remain trusted. This does not delete existing notifications or change schedules. The current proposed SQL locks eligible ticket rows in sorted ID order until the alert job transaction commits to serialize with concurrent reopens. This may delay ticket edits and cause deadlocks or jobs to fail; large deployments need monitoring and load testing.

Rollback restores the previous alert functions, which have ticket-wide deduplication issues, and retains the ledger, cycle column and cycle trigger. The trigger continues tracking reopens. Old-function notifications issued during rollback are not in the ledger and can repeat after reapplication. Reapplication does not reseed stale previous-cycle notifications. No rollback removes or deletes notification history. Check exact existing schema before applying or reapplying; the SQL is not a general drift reconciler.

Synthetic full-schema tests cover initial seed, no reseeding on reapplication, same-recipient and reassignment deduplication, repeat on reopen, lifecycle transitions, client tampering, role access, held tickets and transactional notification failures. A fresh disposable PostgreSQL 17.11 test ran 16 overlapping jobs and held an in-progress reopen while a job waited; one notification per cycle resulted. Auth and cron were synthetic; no hosted GoTrue, Realtime, production workload, pg_cron scheduling or end-to-end browser notification was verified. A later part of the synthetic test required recreating the trigger after changing a synthetic column from text to enum; production does not perform that type conversion.
