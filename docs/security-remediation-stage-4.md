# Transactional audit stream — locally prepared, not deployed

**Later local update:** stage 5 prepares an atomic ticket status/priority/assignment and activity-comment path. It is not deployed; older clients and direct writers still use separate requests. See `security-remediation-stage-5.md`.

`20261101000019_transactional_entity_audit.sql` is a **proposed, unapproved production change**. The live migration history differs from repository timestamps; never use a blanket `supabase db push`. This document is not a recoverable backup. No reset or deletion is authorized.

## Scope and behavior

Five AFTER triggers insert server-generated, structured records for ticket and asset inserts, updates and deletes, plus ticket comments, asset-history rows and maintenance entries. The write and its audit record are in the same transaction: if audit insertion fails, the business write fails too. New/deleted rows contain snapshots; updates contain changed fields only. `actor_id` is derived from `auth.uid()`, not the client-supplied history text or `changed_by`. Jobs and privileged operations without a user claim record a null actor; null must **not** be treated as proof of a particular system process. The identity sequence is not guaranteed to match transaction commit order.

The protected table has no ordinary-user insert/update/delete privileges, and SELECT is restricted to active administrators by RLS. Service/owner or database-administrator powers can bypass or change database protections: this is not a tamper-proof external log. The table deliberately does not cascade on business record or user deletion; deleted comments, maintenance and history remain visible in the audit stream. It stores potentially sensitive ticket descriptions, comments, satisfaction feedback, asset information and user IDs. No retention limit, export process or purge policy is proposed here: agree retention, privacy/access, monitoring and storage capacity before production use. Existing records are not backfilled. Triggers add work to all affected writes and can block normal operations if the audit table fills or an error occurs; measure with realistic volume and monitor failures.

This is an independent structured audit stream, **not** a replacement for the existing user-facing activity/history screens. No audit-screen UI is included. Existing ticket state changes and human remarks are still separate browser requests: a committed change is captured, but a failed remark remains absent. Direct asset-history events can still contain misleading text; this stream records who inserted/deleted it and actual asset changes separately, not whether the claim is truthful. Corrections, audit viewing and retention must be agreed. Historical missing/forged activity is not repaired. Source actor attribution depends on authenticating the original request; service operations and database administrators remain privileged.

## Preflight and proposed rollout

Before considering approval, compare the exact live schema, object names, RLS/grants, all five target tables and their triggers with this migration; check the function owner can write the new table and invoke `auth.uid()`. Verify existing and default grants, admin-role semantics, Realtime interactions, access patterns, storage growth and privacy/retention obligations. Existing `entity_change_audit` objects must match the exact expected schema, constraints, identity, grants and policies; `IF NOT EXISTS` supports rollback/reapplication, not schema reconciliation. Validate full-stack Auth/PostgREST, normal writes, deletion/cascade paths, system jobs and failure recovery on an isolated stack or an explicitly approved controlled test. Agree on operator access and a user-facing timeline before claiming the full history project is complete. No production migration has been approved by this document.

## Rollback

After separate approval, the paired rollback removes the five audit triggers and trigger function while preserving the protected table, read policy and recorded events. **All subsequent writes will be unaudited while rolled back**, and the gap will not be backfilled. Rollback does not undo committed business changes or delete retained audit data. Before reapplying, check exact object definitions and privileges and reconcile policy and storage expectations; reapplying resumes capture but cannot reconstruct the gap. If the audit table or triggers are preventing writes, an approved rollback can restore ordinary writes but gives up this audit coverage.

## Local verification and limitations

Synthetic full-schema tests check administrator/non-administrator read and write permissions, server-attributed actor IDs, entity changes and deleted history, a failed audit insert rolling back its business write, and rollback/reapplication. In a disposable PostgreSQL 17.11 cluster, 12 overlapping authenticated ticket updates yielded 12 attributed audit records; an injected audit failure rolled the associated update back. Other concurrency tests for ticket numbering, SLA delivery and asset creation also passed. These tests use synthetic Auth shims and cannot validate hosted Supabase Auth, PostgREST, production data, pg_cron, Realtime or platform privileges.

Trusted password-change enforcement, real signed-in/session checks, UI audit integration, atomic human remarks, legacy/manual identifier races, staff transition rules, CSP reporting, and migration reconciliation remain outstanding. The profile password flag is still user-editable and frontend-only: it is not a trusted access boundary. No production deployment or migration is implied by local tests.
