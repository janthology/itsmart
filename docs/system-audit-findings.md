# System audit: architecture, security and edge cases

## Scope and safety

The audit reviewed the checked-in application, Edge Functions and migrations at `a8e7204`, inspected the live target's policies, triggers, function definitions, migrations, aggregate data invariants, cron history and service health using read-only queries, and ran synthetic tests locally. No pilot records or production settings were changed. The PostgreSQL authorization tests use PGlite with synthetic rows and a simplified schema, loading the actual checked-in policy and guard functions; relevant live policy and function definitions were checked separately. This is strong evidence of the modeled behavior, but is not an end-to-end exploit against a live authenticated session.

**Test interpretation:** Tests whose names include “characterizes” or “audit” intentionally assert current defective behavior so that the reproductions are durable. A green test run does **not** mean those defects are fixed. When remediating, replace those assertions with the desired behavior.

## Remediation status

The ticket/asset guard migration was applied as production version `20261119024510`; simulated live PostgreSQL role checks passed, but signed-in end-to-end verification remains pending. See `docs/security-remediation-stage-1.md`. Report error-state, ticket partial-success, and create/reset-user mitigations are local-only. Further locally prepared changes address direct history-author spoofing, automatic ticket-number allocation and SLA recipient deduplication, and update jsPDF; see `docs/security-remediation-stage-2.md` for the exact limits, rollout prerequisites and rollbacks. None of these stage-2 changes is deployed. Ticket/asset audit writes remain non-atomic, Auth/profile operations are not transactional, and a trusted mandatory-password-change enforcement design is still open. Remaining issues below are not resolved merely by these local changes.

## Priority findings

### P1 — Authorization and integrity

1. **Original finding: ticket lifecycle fields were not fully protected from a general user.** Before the first guard migration, the trigger allowed creators to modify timing fields and create tickets with arbitrary lifecycle data. The isolated characterization reproduced this risk to SLA, reporting and auto-close. The first guard migration has since been applied, and simulated live PostgreSQL role checks passed for core restrictions, legitimate CSAT and resolved-to-closed/reopen flows. Real signed-in end-to-end verification remains pending. The older characterization tests intentionally preserve the pre-migration reproduction.
2. **Mandatory password-change flag is a UI gate, not a server security boundary.** The self-profile UPDATE policy and trigger allow the user to clear their own `must_change_password` without an Auth password change; the isolated PostgreSQL test reproduced this. Policies and admin Edge Function checks also rely on active role rather than the flag. An authenticated caller can bypass frontend navigation through the API. This means the temporary-password-change requirement is not enforced against a deliberate API client. A secure repair needs a trusted, verifiable password-change completion mechanism and careful compatibility design; simply hiding controls does not fix it.
3. **Audit history is forgeable and not fully atomic.** Staff can directly insert `asset_history` rows with a different `changed_by` (isolated PostgreSQL reproduction). Ordinary asset changes and their history records are also separate browser requests, allowing a change to succeed without its history. Existing admin deletion policies also permit deletion of history and maintenance records. This does not apply to the newer transactional maintenance RPC's normal write path, but it weakens the wider audit trail. Restrict direct writes/deletes as appropriate, derive actor server-side and log state changes transactionally; agree retention and administrative correction requirements first.
4. **Role and workflow rules are enforced inconsistently at the database boundary.** The UI restricts ticket transitions, but live `guard_ticket_update` returns immediately for support and admin; a synthetic support user moved a closed ticket back to open directly. The original asset trigger blocked support status/assignment changes on UPDATE but not INSERT; the first applied guard now blocks the INSERT bypass and simulated live role checks passed. Clarify and enforce the agreed role matrix on the server without silently changing approved support permissions.
5. **Dependency advisories need triage.** The original `pnpm audit --prod` reported 39 advisories across the production dependency graph (2 critical, 13 high, 19 moderate, 5 low). A later local jsPDF upgrade is described in `security-remediation-stage-2.md`; a fresh audit reported eight remaining advisories, including two high advisories for `xlsx@0.18.5`. Audit counts reflect the registry and lockfile at the time of each run. Advisory severity does not by itself establish exploitability in this browser-only usage: several require APIs or input paths the app may not use. Assess reachable code paths, upgrade/replace affected libraries and regression-test PDF/Excel generation. The registry reports no npm patched version for the installed SheetJS advisories.

### P1/P2 — Partial success and recoverability

6. **Admin password reset can change Auth but lose the generated password.** The previously deployed implementation can accept the Auth password update and then lose the password on a profile PATCH failure; its undocumented best-effort session-delete request does not establish revocation. A local-only mitigation checks the flag before and after the Auth request, returns the known password with a warning if the second check fails, and flags uncertain results for operator review rather than silently retrying. Auth/profile writes remain non-atomic, responses can be lost after commit, and the warning is not durable. The local function does not claim session revocation; already issued JWTs can remain valid until expiry. Real Auth behavior and trusted password-change enforcement remain unverified. Evidence: `supabase/functions/reset-password/index.ts`, `edge-functions.security.test.ts` and `security-remediation-stage-1.md`.
7. **User creation compensation is not verified.** Injected tests show a failed profile upsert invokes an Auth-user deletion but ignores a non-success HTTP result, potentially leaving an orphaned/partially configured account. A successful response containing zero profile rows is also treated as success. These are mocked failure cases, not observed production incidents. A local mitigation verifies the returned profile, checks the Auth cleanup response and exposes an operator warning for uncertain outcomes without returning the temporary password. An Auth create response can be lost after commit, cleanup can itself be ambiguous, and there is no automatic durable reconciliation. Real Supabase integration and recovery testing is still needed.
8. **Ticket changes and audit comments are separate writes.** In a mocked browser run the status PATCH succeeded, the comment POST failed, and the UI incorrectly displayed “Failed to update status”; the status had changed and the audit entry was absent. Assignment and priority use the same sequence (source review). Local mitigation: the frontend checks the update returned one row, refreshes even on errors, warns when the activity entry is unconfirmed, retains the intended text temporarily in the page, and avoids automatic retries. Network errors can make either write ambiguous and warnings are lost when leaving the page. This does not make the two writes atomic or repair missing history; an audited, idempotent server operation remains necessary.

### P2 — Operations and data correctness

9. **SLA notification deduplication is ticket-wide, not recipient-aware.** The live at-risk and breach jobs check for any existing notification of the type/link, not for each recipient. Isolated execution reproduced duplicate alerts when requester and assignee are the same person, and a missed alert when the assignee changes after the first notification. Since the notifications table is also cleaned and users can delete their own alerts, removal of the last matching row can permit repeats. Use durable recipient/stage deduplication and define reassign/reopen semantics.
10. **Identifier generation races.** The ticket trigger uses `MAX + 1` without serialized allocation. Two concurrent inserts can choose the same number, one failing on the unique constraint (a source-derived concurrency risk, not load-tested). Asset tags are generated in the browser from the current maximum; synthetic tests show concurrent requests return the same suggestion, and a lookup error silently proposes sequence 1. Unique constraints prevent duplicate records but do not prevent failed operations. Move allocation to concurrency-safe database logic and preserve the previously noted reset/QR-reuse implications.
11. **Report fetch failures look like empty results.** A mocked ticket-report HTTP 500 produced “No data for this report.” The reports page defaults missing query data to empty arrays and does not render query errors. A user may mistake an outage for an empty report. Add clear failure/retry states and prevent exports of incomplete data.
12. **Migration version drift.** Live Supabase migration names match the repository's migrations, but live version IDs were generated by the management API and differ from the timestamp prefixes in local filenames. A standard migration push/reconciliation could misidentify applied migrations. Do not run a blanket `supabase db push` until migration history is reconciled and a safe deployment/rollback process is tested.
13. **CSP is report-only without a configured report destination.** `vercel.json` defines `Content-Security-Policy-Report-Only` but no `report-uri` or `report-to`. Browser console violations can be inspected manually, but there is no configured centralized stream from this header alone from which to conclude a week of clean reports. CSP does not block violations in this mode. Configure monitoring and validate production before enforcement, as previously agreed.

### Investigation / edge cases, not yet reproduced under real concurrency

- The auto-close job derives eligible tickets in a CTE then updates by ID; concurrent ticket activity/reopen versus the scheduled job deserves transaction-level tests to ensure the status and inactivity condition are rechecked after locking.
- Ticket hold duration, resolved/closed times and several transition comments are calculated by the browser clock and multiple requests; clock skew, simultaneous agents, retries and partial failures can corrupt timing or lose activity. Test with concurrent real PostgreSQL sessions and design server-side transitions.
- Report, calendar and dashboard full-table pagination uses offset pages; concurrent inserts/updates during a multi-page fetch can yield omissions or duplicates. Performance/load and large-data behavior have not been established by small fixtures.
- Actual production CORS, Edge Function gateway/startup behavior, authenticated RLS across all roles, multi-device session revocation, Realtime events, keyboard/screen-reader behavior, print outputs and backup/restore were not fully exercised here. A staging database branch was previously unavailable on the current plan; use an isolated test project/environment rather than destructive production testing.

## Read-only live observations

- The project's Auth, database, REST, pooler and storage health checks were healthy. Realtime initially reported unhealthy, then healthy on a second check; the second response showed no DB/replication connection. This is a transient observation, not proof of an active incident or of working subscriptions. Verify an actual subscription and monitor health.
- Last-seven-day cron history returned successful runs for PM alerts, SLA alerts, auto-close and cleanup, with no failed rows returned in that aggregate. This verifies reported job execution, not correctness of every notification or ticket.
- Aggregate ticket checks found no negative hold values, missing relevant terminal/hold timestamps, reversed resolution times, or active tickets with a resolved timestamp among the 27 records inspected.
- Of 26 existing assets, 19 have no next PM date while PM is required: 18 are retired and one is active. One active asset has next PM on or before Last PM. These may be legacy records deliberately preserved during cutover; review them, do not silently rewrite them. Counts may change over time.

## Recommended order

1. Agree server-side authorization and temporary-password completion design; remediate P1 issues with compatibility tests and staged/rollback-safe migrations.
2. Address reset/create and ticket/asset partial-success paths and secure the audit trail; add real isolated integration and concurrent-session tests.
3. Upgrade/replace vulnerable dependencies after confirming usable versions and export compatibility.
4. Correct recipient-specific alerts, safe numbering, reports errors, migration drift and observability; validate existing PM exceptions.
5. Perform a role-by-role manual review and real backend/security tests in an isolated environment, verify backup/restore, and only then revisit the separately approved pilot reset plan.
