## Scope

`20261101000020_ticket_change_with_activity.sql` adds `update_ticket_with_activity`, an invoker-security function for status, priority and assignment changes. The local SQL explicitly revokes execution from `service_role` and anon, retaining authenticated execution despite Supabase default grants; privileged database owners remain outside that restriction. It locks the ticket, rejects stale `updated_at`, validates the allowed fields and required remarks, derives the actor and activity summary server-side, applies the change, and inserts its activity comment in the same transaction. A failed comment rolls the ticket change back. Closing retains the assignee. Hold duration and lifecycle timestamps for these changes use the database clock. Existing RLS, active-user checks and ticket guards run as the caller; it does not grant support staff or general users any additional write permissions. Staff transition enforcement beyond existing guards is not included.

The prepared frontend uses this RPC for those three actions. A lost response can mean the transaction committed. Before sending, the client stores a per-user/ticket action marker in same-tab `sessionStorage`, without storing names, remarks or ticket content. An ambiguous result or reload blocks further status/priority/assignment changes until the user checks the refreshed ticket and activity and explicitly acknowledges the warning; unreadable or unwritable storage prevents sending. Remarks remain visible only on the current page and are lost on reload. The marker is not durable across tab closure, storage clearing, other tabs/devices or browser profiles; it is not a server-side idempotency key. The RPC has no request-id ledger, so users must inspect results before retrying. Concurrent changes can cause a stale-version error requiring refresh. Type changes still use the existing direct update, though the separately prepared structured audit stream records them if applied. Other API/direct legacy writes remain possible and can bypass this atomic activity path. The user-facing text is derived from actual before/after state but retains user-provided remarks, which can be inaccurate. This function does not enforce a new role/transition matrix.

## Preflight, rollout and rollback

Read-only preflight found the target RPC absent, the nine ticket columns, four comment columns, two profile columns and two enum types used by it present, and the active-user helper and ticket guard definitions at MD5 `52f98a52eadabcc1ea3e648d517db7ac` and `d1ff5837272ff3fe4fb27449a0d697c0` respectively. Existing ticket/comment policies still grant active staff broad writes and owners scoped writes. The observed counts were 27 tickets and 200 comments. Ticket, comment and profile RLS was enabled; authenticated table grants are subject to their policies. Nine non-internal ticket/comment triggers were enabled, including the update guard and comment notification/touch triggers. `ticket_status` has `open`, `assigned`, `in_progress`, `resolved`, `closed`, `on_hold`; `ticket_priority` has `low`, `medium`, `high`, `critical`. This is point-in-time metadata, not a complete drift or security check; reconfirm immediately before any approved change. Before approval, finish comparing live ticket/comment schemas, triggers, grants, timestamp handling, role matrix and current frontend against the local chain. Test admin, support and owner changes, authorization denials, stale-version and disconnected responses with approved dedicated test accounts and separately approved synthetic records. Confirm all active frontend and API writers; old clients still perform separate writes. The database RPC must be applied and verified before the new frontend is deployed, otherwise status/priority/assignment changes from the new frontend will fail. A user-facing notice should ask users to refresh stale tabs. Production migration and frontend deployment each require the previously agreed specific review and approval.

For rollback, separately approve and roll back the new frontend first, then run the paired SQL to drop this RPC. Existing ticket updates, comments, and any structured audit events remain untouched. The legacy frontend resumes its separate requests and can again leave a change without a corresponding activity comment. Rollback cannot reverse business changes and does not address old clients or historic gaps.

## Verification and outstanding work

Full-chain synthetic tests cover administrator/support and owner actions, retained assignment, server-derived actor, required remarks, stale writes, unauthorized changes, hold duration, injected comment failure/transaction rollback, rollback/reapplication, and revocation of a synthetic service-role default grant. Mocked browser cases exercise successful and lost-response handling for status, priority and assignment, marker restoration after reload, blocked storage and preservation of unsent remarks; they do not test the real PostgREST/Auth stack. The latest local run passed 159 unit tests, 54 mocked browser tests, typecheck, build and bundle budget. An earlier `pnpm audit` reported no known advisories at that time. Larger workloads and production integration remain to be checked.
