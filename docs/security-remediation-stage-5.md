## Scope

`20261101000020_ticket_change_with_activity.sql` adds `update_ticket_with_activity`, an invoker-security function for status, priority and assignment changes. It locks the ticket, rejects stale `updated_at`, validates the allowed fields and required remarks, derives the actor and activity summary server-side, applies the change, and inserts its activity comment in the same transaction. A failed comment rolls the ticket change back. Closing retains the assignee. Hold duration and lifecycle timestamps for these changes use the database clock. Existing RLS, active-user checks and ticket guards run as the caller; it does not grant support staff or general users any additional write permissions. Staff transition enforcement beyond existing guards is not included.

The prepared frontend uses this RPC for those three actions. A lost response can mean the transaction committed: the UI refreshes, preserves intended remarks in a page-local warning and does not automatically retry. The warning is not durable across navigation or reload. The RPC does not have a request-id ledger, so a user must inspect the updated ticket and activity before manually retrying. Concurrent changes can cause a stale-version error requiring refresh. Type changes still use the existing direct update, though the separately prepared structured audit stream records them if applied. Other API/direct legacy writes remain possible and can bypass this atomic activity path. The user-facing text is derived from actual before/after state but retains user-provided remarks, which can be inaccurate. This function does not enforce a new role/transition matrix.

## Preflight, rollout and rollback

Before approval, compare live ticket/comment schemas, triggers, grants, RLS, timestamp handling, role matrix and current frontend against the local chain. Test admin, support and owner changes, authorization denials, stale-version and disconnected responses with approved dedicated test accounts. Confirm all active frontend and API writers; old clients still perform separate writes. The database RPC must be applied and verified before the new frontend is deployed, otherwise status/priority/assignment changes from the new frontend will fail. A user-facing notice should ask users to refresh stale tabs. Production migration and frontend deployment each require the previously agreed specific review and approval.

For rollback, separately approve and roll back the new frontend first, then run the paired SQL to drop this RPC. Existing ticket updates, comments, and any structured audit events remain untouched. The legacy frontend resumes its separate requests and can again leave a change without a corresponding activity comment. Rollback cannot reverse business changes and does not address old clients or historic gaps.
