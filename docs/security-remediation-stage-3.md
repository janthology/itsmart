## Atomic asset creation and tag allocation

`20261101000018_create_asset_atomically.sql` adds protected per-year counters and an actor/request-id ledger, plus a security-definer RPC for active administrator/support creation. It allocates a `DOST02-ITA` + Philippine-local year + at least six-digit sequence, inserts the asset, inserts a creation history row with `auth.uid()`, and records the outcome in one transaction. It rejects unknown request fields and support requests for a non-active or assigned asset. A retry by the same actor with the same ID and identical JSON returns the original asset; changed payload or a deleted result is rejected. An aborted transaction rolls back the counter, ledger, asset and history together. It does not automatically retry serialization errors.

The local frontend uses this RPC and no longer permits entry of a manual creation tag. A lost response may have committed: retrying identical details from the still-mounted page reuses the ID, while changed details are blocked pending explicit acknowledgement. The ID and warning are **not persistent** across reload/navigation and there is no server-side search/recovery screen. Users must check the asset list before starting a new request after leaving or explicitly clearing the warning. Existing direct insert writers remain enabled for compatibility, and can race the RPC/manual tags or create records without transactional creation history. The database unique constraint is the final collision defense; it does not serialize manual writers. Existing asset edits and ticket changes still do not all have transactional, unforgeable history. This migration does not address those gaps.

Preflight before any approval: compare the live schema, RLS/policies, function/trigger bodies and unique asset-tag constraints with the repository; verify all active frontend/API/manual writers, current tag formats (including nonnumeric or unusually long suffixes), case variations, and future-year/manual values. Review performance of the MAX scan and resolve mismatched existing objects rather than relying on `IF NOT EXISTS`. Confirm active staff policies and asset field/date validation match this RPC. Define a coordinated deployment and direct-write cutover; stale clients currently keep their prior path. Counter creation retains existing high-water marks, but it cannot guarantee collision-free coexistence with concurrently supplied manual tags. Confirm real PostgREST response and user workflows with approved test accounts before production rollout. `00015`–`00017` are independent prepared migrations and do not become approved by this document.

**Ordering:** the new frontend cannot create assets until this RPC exists. Apply the reviewed database migration first only after separate approval and postflight, then separately deploy the compatible frontend when approved; verify both current and new clients and advise users about ambiguous retry handling. Do not apply or deploy based solely on synthetic tests.

**Rollback:** first stop or roll back the new frontend so it stops calling the RPC, after separately approving the rollback. The accompanying rollback drops the RPC and leaves the protected counter and request ledger (and all created assets/history) intact. Old frontend resumes direct writes and client-side tag allocation, reopening race/missing-history risks. Rollback does not remove or reverse committed business records. While rolled back, counters are not advanced by direct writes; reapplication scans existing tags and must reconcile retained high-water marks, manual writers and the ledger. If reverting to an older spreadsheet frontend, reassess its known vulnerabilities and CSP independently. Production rollback itself requires approval.

Synthetic full-chain tests verify roles, retry/payload mismatch, attribution, failed-history atomicity and rollback/reapplication. In a disposable local PostgreSQL 17 cluster, 16 concurrent creates produced distinct tags and 12 overlapping retries of one request produced a single asset and history row. These are not live PostgREST/Auth tests and don't prove safe coexistence with manual writers. The security concurrency script must only target a fresh disposable local cluster; see stage 2 documentation.

## Dependency and export remediation

The unmaintained vulnerable `xlsx` package was removed; reports use `write-excel-file` and tests read generated files with `read-excel-file`. Strings, including leading `=`, are written as strings rather than formulas, and numbers remain numeric. Synthetic browser exports cover performance and depreciation; all other reports, larger workbooks and worker execution under actual deployed CSP still need production-like validation. The Report-Only CSP adds `worker-src 'self' blob:` because large asynchronous compression can create blob workers. It is not an enforced CSP or a configured reporting destination; collect and review reports before enforcement as previously agreed.

The lockfile also upgrades jsPDF, Vite, Zod and its form resolver, and several transitive dependencies. Scoped overrides cover compatible runtime packages and typography's specifically pinned older selector parser; the workspace's existing global esbuild pin was advanced to 0.28.1 alongside a compatible tsx update. Zod's form type changes preserve numeric coercion; run real form validation before rollout. The full and production `pnpm audit` commands both reported **no known advisories** on this lockfile at test time. Audit counts change with the registry, do not guarantee security or reachability, and `--prod` classification alone is insufficient because several build dependencies are bundled into the frontend. No frontend deployment occurred. Build emits existing sourcemap/chunk warnings.

## Remaining work and live checks

Trusted mandatory password-change enforcement is not implemented: the profile flag remains user-editable and frontend-only. A safe design needs a server-controlled state, proof that a password actually changed, access checks covering RLS and all RPCs/functions, stale-JWT/session revocation behavior, reset/recovery and service/admin access without lockout. Existing local reset mitigations do not establish that boundary. Ticket comments/history and most asset changes remain non-atomic with their associated writes, and users with permission may still create misleading history content. Manual/legacy tag and number writers remain a race. Staff transition semantics, notification policy, PM exceptions, CSP reporting and monitoring also remain to be reviewed.

Real signed-in Supabase UI/Auth/PostgREST, reset/session, cron, Realtime, and concurrent production checks have **not** been performed. The connector's SQL role simulation is not a real sign-in; sandbox network restrictions and the lack of isolated staging prevent equivalent automated checks. Agree on user-operated, dedicated test accounts and clearly marked synthetic test records and cleanup/retention rules before live tests; do not share passwords, tokens, or modify existing business records for testing. Test accounts and records are not created by this change. Do not deploy the prepared reset Edge Function merely to perform tests.
