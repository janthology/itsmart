# Pilot-readiness test findings

Tested against a local production build using synthetic browser sessions and intercepted Supabase requests. No pilot data was reset or modified. The role-page fixture denies writes by default; individual password-flow requests are simulated locally. These checks are not a substitute for a live-backend authorization/integration test or a manual UX review.

## Confirmed issues to triage

1. **Password change: partial success is reported as complete.** If Auth accepts the new password but the subsequent profile flag/timestamp update fails, the update error is ignored, the UI reports success and clears the local mandatory-change flag. The server-side flag may remain set, causing a future redirect back to password change; importantly, the password may already have changed. Reproduced with a mocked 403 profile update. Any repair must account for this partial-success state and tell the user which password is now valid.
2. **Maintenance/history read errors can look like empty records.** The asset detail page defaults each query's data to an empty array and checks loading but not errors. A mocked maintenance-log 500 produced “No maintenance records yet.” History uses the same pattern (source-reviewed, not independently error-injected). This could mislead users during an outage.
3. **Unassigned-assets Excel export mislabels asset age.** “Days Unassigned” is calculated from the purchase date, not an assignment/unassignment event. A previously assigned asset can therefore show a misleading duration. The PDF does not contain this column.
4. **Zero-cost asset depreciation can be NaN.** Both preview and export divide by purchase value to calculate the percentage. A synthetic zero-cost record produced NaN in the Excel data. Future-dated purchases can also yield negative accumulated depreciation and a current value above cost (source-reviewed); choose the intended policy for zero and future dates before fixing.
5. **Password form accessibility.** The three visual labels on the change-password page are not programmatically associated with the inputs; the two password visibility icon buttons also lack accessible names (source-reviewed). The missing current-password association was reproduced by a browser accessibility locator.

The specific defects are recorded as expected-failure tests (`test.fail` / `it.fails`); they are not passing product behavior. When fixing an issue, remove its expected-failure marker and update the assertion as appropriate. The browser setup assertions run before enabling the expected-failure marker so fixture problems cannot masquerade as the expected defect.

## Coverage and limits

- Automated browser smoke visits dashboard, asset list/detail, ticket list/detail, calendar, reports, profile, change password and not-found with each of administrator, support staff and general user. Separate tests check user-management access and selected ticket/report controls; existing tests cover maintenance forms and performance reports. Signed-out tests cover login, redirects and the manifest.
- One general-user synthetic-data run checks document-level horizontal overflow at a 390px viewport after each page renders. It does not prove visual quality, dialog usability, keyboard navigation, zoom support, or that every element fits.
- Unit tests cover date/SLA calculations, performance exports, mappings, pagination, dashboard metrics, user filters and labels. The full-source V8 unit-coverage measurement on this run was **5.45% lines, 5.88% branches**; browser coverage is not included. Run `corepack pnpm --filter @workspace/itam run test:coverage` to repeat it.
- Important unverified flows include real authentication/password updates, full ticket lifecycle and comments, user creation/reset, asset creation/assignment, report downloads beyond targeted mock checks, real notification and cron behavior, and backend enforcement under actual sessions. Mocked UI authorization does not prove RLS. Previous maintenance-specific rollback-only database checks are separate from this audit.
- Before reset, do a manual role-by-role pass using `docs/smoke-test-checklist.md` against an isolated test environment with disposable accounts and records, plus error, accessibility, mobile/zoom and print checks. Do not use destructive production tests or delete pilot data without separate approval and a verified backup.
