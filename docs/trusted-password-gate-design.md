# Trusted password-change gate — design and local operation prototype

**Not implemented and not deployment-ready.** `supabase/proposals/password-gate/operations.sql` is a state-machine experiment, not a migration; it is deliberately outside `supabase/migrations`. It does not protect data, verify a password change, validate JWTs, or update the existing Edge Functions/UI. The existing `profiles.must_change_password` remains editable by a user and is only a frontend gate. Do not apply the prototype to production.

A separate local frontend-only recovery aid marks an in-flight self-service password change in same-tab `sessionStorage` before sending the Auth update. If the response is ambiguous or the page reloads before the profile update completes, it asks the user to review the result before another attempt. It stores no password, and blocks a new attempt when storage cannot be used. This is not the trusted gate: tab closure, storage clearing, other devices/tabs, late Auth responses, concurrent resets and direct API calls bypass it; explicit acknowledgement does not prove the result or fence a still-running request. Actual Auth/session behavior and recovery remain unverified.

## Security requirements

A trusted gate must prevent a user with a temporary password, an old session or a forged profile update from accessing application data and privileged functions until the password has genuinely changed. It must retain a usable recovery path without exposing service credentials or passwords and must not lock out the retained administrator. A value on an editable profile is not evidence of a password update; merely comparing bcrypt hashes is insufficient because rehashing the same plaintext can yield a different hash. Do not send plaintext passwords to a SQL RPC or include them in logs, audit rows, URLs, exceptions, or chat.

A proposed implementation needs all of the following, tested as a system:

1. **Protected state and serialization.** A service-controlled gate, initialized before a temporary password is delivered, blocks overlapping reset/change attempts. No automatic retry of an ambiguous Auth mutation. An operation is not made safe merely by adding a timeout: an older network request might finish after the timeout and race a newer operation. Any recovery must fence or otherwise rule out such late effects, and provide a deliberate, tested administrator procedure for stuck operations.
2. **Trusted change proof.** A narrowly scoped service verifies the caller and current password using supported Auth APIs, enforces a new password distinct from the current password, requests the Auth change, and only marks the matching operation complete after a confirmed success. Completion must be service-only and cannot accept a user-supplied assertion. A lost Auth response may leave the account locked; do not guess success. Rate-limit and redact sensitive handling. The security model must also consider a user changing Auth directly, account creation, normal voluntary changes, recovery links, and a concurrent admin reset.
3. **Real sessions and stale JWTs.** Validating the JWT signature alone does not prove that the corresponding session remains valid after reset/sign-out. Check the JWT's authenticated `session_id` against the target user's live `auth.sessions` where supported, fail closed when absent/expired, and verify actual hosted Auth semantics, schema ownership and privileges. A read-only metadata check confirmed the target has `auth.sessions.id`, `user_id`, and `not_after`, and `auth.users.id` and `encrypted_password`; it did not inspect session records, password hashes or runtime behavior. Direct Auth endpoints and all service-backed Edge Functions require separate review. Checking sessions can affect other JWT consumers and performance.
4. **Complete authorization surface.** Enforce the trusted state for public and private table policies, security-invoker views, Realtime, all exposed security-definer RPCs and Edge Functions. Existing `get_my_role`/`is_active_user` are not enough on their own; examine self-profile exceptions and every direct grant. Preserve only the minimum self-access required to finish changing a password; block a self-clear of the profile flag. Service/cron bypasses must be narrowly limited and explicit. Verify that profile directory lookups, CSAT, PM notification inserts, maintenance and existing role behavior are not broken.
5. **Safe cutover.** Add non-enforcing infrastructure first, deploy compatible handlers and UI in a reviewed order, then activate enforcement only after real role/session integration tests and an independently reviewed rollback. Reconcile every current account, especially legacy accounts whose editable flags may already be incorrect; do not infer that an unflagged account is trustworthy. Retain admin access and explicitly plan recovery for in-progress or orphaned operations. Each production migration, Edge Function/frontend deployment and rollback requires separate review and approval; do not blanket-push mismatched migration histories.

## What the prototype covers

The isolated prototype records service-only reset/change phases and operation IDs; no ordinary authenticated user can call those prototype operations or read its table. A second in-progress reset/change is rejected, stale completions cannot clear a later operation, and ambiguous operations remain in progress. The prototype includes a pre-Auth-attempt cancellation helper, which is safe **only if** a trusted caller knows no Auth password mutation was sent; using it after an ambiguous response is unsafe. The prototype trusts its service caller to know an actual password change succeeded, so it is not sufficient on its own and it must not be exposed to an ordinary user.

Synthetic PGlite tests cover role grants, transitions, repeated acknowledgements, stale completions and failure handling. A disposable PostgreSQL test also exercised concurrent operation starts. Service-level access and database administrators remain trusted. The user specified three-year audit retention; cutoff interpretation, legal holds and any purge mechanism still require review. No purge or production operation is authorized by this design.

### Additional isolated authorization and Edge research

`authorization.sql` experiments with restrictive RLS on synthetic tables, session ownership/expiry, a self-profile read exception, a sample gated definer function and protection of profile password fields. It requires a session created after the gate completion timestamp; old sessions fail closed in the synthetic test even if still present. `change-password.ts` sketches the service flow: require a live user and required gate, serialize, reverify the current password, attempt the Auth update, globally sign out, then clear the operation; ambiguity after mutation remains locked. The user must sign in again after completion. These files are not migrations or deployed handlers. Mock tests merely assert request ordering and failure responses; PGlite uses synthetic Auth sessions and deliberately permissive policies. They **do not** prove password change, session revocation, runtime Auth compatibility, rate limiting, Edge gateway behavior, actual RLS integration, Realtime or browser behavior.

A full-chain synthetic test now demonstrates a concrete bypass: while prototype table RLS blocks a support user's asset reads during `resetting`, the unmodified `get_my_role()` still returns support, so the repository's SECURITY DEFINER `record_asset_maintenance` and proposed `create_asset_with_history` can write as that user. Both now exist in production (asset creation was subsequently applied as migration `20261120083024`). The test did **not** exercise the hosted deployment or prove an exploitable hosted JWT. `role-helpers.sql` experiments with gating `get_my_role` and `is_active_user`: in this synthetic scenario it blocks both demonstrated writes and restores the helpers after a service assertion and a later session. That assertion is not proof of an Auth change, and this experiment may break onboarding, cron, profile access and recovery. It does not cover functions or Edge endpoints that bypass these helpers. It is not a migration and must never be applied to production.

### Explicit session-admission experiment

A new local-only `session-authorization.sql` and `login-broker.ts` explore the sign-in race instead of trusting session timestamps alone. The broker snapshots an active account's password-operation generation **before** asking GoTrue to verify the password, checks the returned identity and session, and asks a service-only SQL function to admit that session only if the generation is still cleared and unchanged. The SQL locks the gate row while checking the generation and validates session ownership, creation time and expiry. An admitted-session row is tied to the Auth session and generation; reset/change invalidates the generation, and deleting the Auth session cascades its admission row. For a `required` gate, a separate confirmation permits a restricted session for the password-change path without admitting it to business data. The `admission-integration.sql` experiment substitutes that predicate for the sample RLS/role-helper design. A caller must never supply the session ID or assert verification; the broker derives it from the GoTrue response and checks the user with Auth. The database still trusts the privileged broker: a service that admits an old or unverified session can defeat the design.

Synthetic tests demonstrate that a late-created session would pass the **older timestamp-only experiment** yet fails the admission check; they simulate, but do not reproduce, an actual GoTrue race. They cover generation changes during simulated admission, wrong user/session, expiry, inactive accounts, stale snapshots, permission denial and restricted recovery. Mocked Edge tests check operation order, credentials not being returned on failures, and best-effort logout. In a rolled-back full-schema PGlite experiment, unadmitted sessions were blocked by restrictive policies and experimental role helpers; admitted sessions could call the five sampled business definer RPCs within their normal roles; a later reset blocked table reads and the sampled maintenance call again. A disposable PostgreSQL 17.11 test also held a reset transaction's row lock while admission waited, verified the stale admission was rejected after reset committed, and verified that a later reset invalidated an admitted synthetic session. This is a real database concurrency test with synthetic Auth tables, not a GoTrue concurrency test. A read-only production catalog inventory found those five plus the two role helpers as the seven currently exposed public non-trigger security-definer functions; this is point-in-time metadata, not a complete API, Edge, trigger, view, Realtime, extension or service-role audit. Hosted `auth.sessions.created_at` is nullable; the experiment fails closed if it is null, which could block legitimate users. No live Auth records, passwords, sessions or settings were changed.

**Still not deployable:** the broker and SQL are isolated prototypes, not wired into the frontend, real reset/create/change functions, or active production policies. Required-change completion, initialization of existing accounts without assuming editable flags are trustworthy, safe administrator recovery, service and cron paths, rate limiting, MFA, request size handling and real GoTrue/PostgREST/Realtime compatibility are unfinished. Email matching, timestamp semantics, Auth session IDs through refresh, privileges and FK behavior against managed Auth must be verified. A lost admission response plus failed logout can leave an admitted orphan; a lost sign-in response can leave an untracked session. Other Auth endpoints remain accessible, and correctness depends on complete data and definer/Edge coverage. Database checks cannot retract data already returned; transactions or statements using an earlier snapshot may finish after a reset begins and require explicit concurrency analysis. The broker can leak account state through timing, uses privileged credentials, and lacks production abuse controls. A real login implementation must not expose service credentials or log passwords or tokens. Service/database owners bypass RLS. No deployment, migration, account reset or recovery operation is authorized by these experiments.

The prior password-change Edge prototype also creates a temporary session for re-verification; cleanup, GoTrue endpoint semantics, error paths, service-key usage and ambiguous outcomes remain unresolved. A trusted state cannot safely be completed merely by accepting a client assertion. The current profile flow is unchanged and insecure as a trusted gate. Do not apply or deploy these proposals.
