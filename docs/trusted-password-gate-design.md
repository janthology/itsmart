# Trusted password-change gate — design and local operation prototype

**Not implemented and not deployment-ready.** `supabase/proposals/password-gate/operations.sql` is a state-machine experiment, not a migration; it is deliberately outside `supabase/migrations`. It does not protect data, verify a password change, validate JWTs, or update the existing Edge Functions/UI. The existing `profiles.must_change_password` remains editable by a user and is only a frontend gate. Do not apply the prototype to production.

## Security requirements

A trusted gate must prevent a user with a temporary password, an old session or a forged profile update from accessing application data and privileged functions until the password has genuinely changed. It must retain a usable recovery path without exposing service credentials or passwords and must not lock out the retained administrator. A value on an editable profile is not evidence of a password update; merely comparing bcrypt hashes is insufficient because rehashing the same plaintext can yield a different hash. Do not send plaintext passwords to a SQL RPC or include them in logs, audit rows, URLs, exceptions, or chat.

A proposed implementation needs all of the following, tested as a system:

1. **Protected state and serialization.** A service-controlled gate, initialized before a temporary password is delivered, blocks overlapping reset/change attempts. No automatic retry of an ambiguous Auth mutation. An operation is not made safe merely by adding a timeout: an older network request might finish after the timeout and race a newer operation. Any recovery must fence or otherwise rule out such late effects, and provide a deliberate, tested administrator procedure for stuck operations.
2. **Trusted change proof.** A narrowly scoped service verifies the caller and current password using supported Auth APIs, enforces a new password distinct from the current password, requests the Auth change, and only marks the matching operation complete after a confirmed success. Completion must be service-only and cannot accept a user-supplied assertion. A lost Auth response may leave the account locked; do not guess success. Rate-limit and redact sensitive handling. The security model must also consider a user changing Auth directly, account creation, normal voluntary changes, recovery links, and a concurrent admin reset.
3. **Real sessions and stale JWTs.** Validating the JWT signature alone does not prove that the corresponding session remains valid after reset/sign-out. Check the JWT's authenticated `session_id` against the target user's live `auth.sessions` where supported, fail closed when absent/expired, and verify actual hosted Auth semantics, schema ownership and privileges. A read-only metadata check confirmed the target has `auth.sessions.id`, `user_id`, and `not_after`, and `auth.users.id` and `encrypted_password`; it did not inspect session records, password hashes or runtime behavior. Direct Auth endpoints and all service-backed Edge Functions require separate review. Checking sessions can affect other JWT consumers and performance.
4. **Complete authorization surface.** Enforce the trusted state for public and private table policies, security-invoker views, Realtime, all exposed security-definer RPCs and Edge Functions. Existing `get_my_role`/`is_active_user` are not enough on their own; examine self-profile exceptions and every direct grant. Preserve only the minimum self-access required to finish changing a password; block a self-clear of the profile flag. Service/cron bypasses must be narrowly limited and explicit. Verify that profile directory lookups, CSAT, PM notification inserts, maintenance and existing role behavior are not broken.
5. **Safe cutover.** Add non-enforcing infrastructure first, deploy compatible handlers and UI in a reviewed order, then activate enforcement only after real role/session integration tests and an independently reviewed rollback. Reconcile every current account, especially legacy accounts whose editable flags may already be incorrect; do not infer that an unflagged account is trustworthy. Retain admin access and explicitly plan recovery for in-progress or orphaned operations. Each production migration, Edge Function/frontend deployment and rollback requires separate review and approval; do not blanket-push mismatched migration histories.

## What the prototype covers

The isolated prototype records service-only reset/change phases and operation IDs; no ordinary authenticated user can call those prototype operations or read its table. A second in-progress reset/change is rejected, stale completions cannot clear a later operation, and ambiguous operations remain in progress. The prototype includes a pre-Auth-attempt cancellation helper, which is safe **only if** a trusted caller knows no Auth password mutation was sent; using it after an ambiguous response is unsafe. The prototype trusts its service caller to know an actual password change succeeded, so it is not sufficient on its own and it must not be exposed to an ordinary user.

Synthetic PGlite tests cover role grants, transitions, repeated acknowledgements, stale completions and failure handling. A disposable PostgreSQL test also exercised concurrent operation starts. These are not tests of GoTrue, session revocation, RLS integration, Edge Functions, the browser, late Auth responses or recovery. Service-level access and database administrators remain trusted. The chosen audit-retention policy has not yet been provided; no purge policy or production operation is authorized by this design.
