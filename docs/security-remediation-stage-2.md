## Asset-history actor guard

`20261101000015_asset_history_actor_guard.sql` changes only the existing `asset_history_insert_staff` policy: an authenticated active administrator or support user can directly insert only with their own `auth.uid()` as `changed_by`. The existing UI supplies that value; an absent/unconfirmed Auth user now causes the history insert to be rejected. The maintenance RPCs use server-derived actors and run as security-definer functions, while service-role writes retain their bypass. Isolated full-schema tests cover staff, administrator, inactive/general users, service role, legitimate maintenance and rollback.

This is **not** a complete audit solution: staff can still invent an event and values under their own identity, direct asset mutation and history are separate requests, history may be missing after a partial failure, and existing delete permissions are unchanged. An Auth lookup failure after a successful asset write can now leave history missing, so review the current UI's partial-failure handling and test stale sessions before rollout. Server-derived transactional history, idempotency, and an explicit retention/correction policy remain necessary.

Preflight: compare the live policy and relevant grants/maintenance RPC definitions, current deployed frontend's actor behavior and active sessions; verify there are no other writers relying on null or a different actor. The rollback file restores the old permissive insert check, reopening actor spoofing; neither direction corrects historical entries. Rollback requires separate approval.

## Ticket-number allocator

`20261101000016_ticket_number_allocator.sql` creates a protected, RLS-enabled per-year high-water table and changes the existing trigger function to atomically allocate through an upsert. It seeds against current numbers on each invocation, retains the high-water mark after deletion, and permits more than five sequence digits rather than truncating at 100000. The frontend's existing automatic insert path and ticket-number format are otherwise retained. Authenticated and anonymous users have no direct counter-table privileges. IDs allocated in aborted transactions may be reused because their writes roll back.

In a disposable PostgreSQL 17.11 cluster, 24 overlapping authenticated-role insert transactions completed with distinct consecutive automatic numbers; rollback of an uncommitted allocation was also checked. The full synthetic schema tests cover existing manual numbers, the six-digit boundary, deletion, role permissions, rollback and reapplication. This is not proof for all isolation levels, failures or production data: serializable/repeatable-read transactions may need retries, manual staff-supplied ticket numbers can race the automatic path, and the existing unique constraint remains the final protection. Asset-tag allocation remains separate and unresolved.

Before rollout: compare the production trigger/function, grants, the unique constraint, existing number formats and any explicit-number writers. Verify the counter table is absent or exactly matches the prepared schema and its permissions. The rollback restores the previous MAX+1 function and its races/possible number reuse; it **retains** the protected counter table and its committed high-water marks. While rolled back those marks are not used. Reapplication must reconcile both the retained marks and numbers created in the meantime. An existing divergent counter table must not be silently accepted just because the migration uses `IF NOT EXISTS`.

## SLA recipient deduplication

`20261101000017_sla_recipient_dedup.sql` prepares a protected delivery ledger and updates the two existing SLA functions, without changing cron schedules or eligibility thresholds. The proposed policy is one alert per **ticket, recipient and stage for the lifetime of the ticket**: duplicate requester/assignee identities receive one alert; a newly assigned user can receive their own alert; deleting a notification, assigning away and back, or reopening does not reset an already-delivered stage. This proposed reopen and retention behavior needs explicit review before production use. Ledger entries persist until the related ticket/profile is deleted.

Existing still-present SLA notifications are seeded into the ledger before replacing the functions. Notifications already deleted or removed by retention cannot be reconstructed, so a qualifying recipient may receive a further alert after cutover. The unique key and transactional ledger/notification writes are intended to prevent duplicate deliveries from overlapping jobs, but failure or deadlock may still abort a job and require a later run. A real PostgreSQL 17.11 test ran 16 overlapping jobs for one requester/assignee and observed one ledger entry and one notification. Synthetic full-schema tests cover seeding, reassignment, deletion, reopen, hold exclusion, separate breach stage, permission denial, notification failure rollback and rollback/reapplication. They do not run real pg_cron or production Realtime.

Before rollout: compare live function definitions, table/grants, cron commands and schedules; validate existing notification/link format, seed volume, retention expectations and proposed reopen behavior. If the ledger already exists, verify its exact schema and content before using `IF NOT EXISTS`. The rollback restores old ticket-wide deduplication and preserves the protected ledger, but the restored functions ignore it. Notifications created during rollout or rollback are not deleted, and future reapplication must seed again. Rollback reopens duplication/missed-recipient behavior and requires separate approval.

## Local tests and limitations

The full repository migration chain passed in disposable PGlite with synthetic Auth/cron/publication shims. The full local suite passed **118 Vitest tests**, and **51 mocked Playwright tests** passed after the PDF upgrade. Typecheck, build and bundle budget passed. A separate script `corepack pnpm --filter @workspace/itam run test:security:postgres` exercises concurrent independent PostgreSQL sessions against a fresh disposable local cluster. It requires `ITSMART_DISPOSABLE_PG=1`, `ITSMART_TEST_PG_SOCKET` pointing to a temporary Unix socket, and optionally `ITSMART_TEST_PG_PORT`; it creates and removes roles and a randomly named database. **Never point it at production, Supabase, a shared database or a cluster with valuable data.** The script refuses non-temporary sockets/data directories, existing app roles, public tables and other non-template databases, but these checks are not a substitute for a truly disposable cluster. It is not part of the normal CI run and does not model Supabase Auth/PostgREST/Realtime or real cron.

Remaining work includes trusted mandatory-password enforcement and actual session behavior, transactional ticket/asset history and partial-failure recovery, safe asset-tag allocation, migration-history reconciliation, CSP reporting and monitoring, remaining dependency advisories, PM exceptions, live signed-in role checks, real Supabase integration/accessibility testing and the separately approved pilot reset plan. The earlier reset/create mitigations remain local-only. Do not interpret this stage as completion of the entire system-hardening plan.
